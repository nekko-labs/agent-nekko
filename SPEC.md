# Spec, Agent Nekko

> **This is the source of truth for the project.** It describes *what* we're building and *why*, vision, users, journeys, the feature set, and what success looks like. It is **not** about stack or technical design (that's `TASKS.md`). It is a **living artifact**: every prompt that adds or changes a feature updates this file so it always describes the system as it actually is and intends to be. The verbatim origin ask lives in [original-prompt.md](../../obsurdian/projects/agent-nekko/original-prompt.md).

## Vision

**Agent Nekko** (formerly Agent Nekko, briefly Nekkos, and originally Open Paw) is your local agent, backed by frontier intelligence. It is an open-source assistant for coding, cowork, and repeatable work that blends models running on your hardware with frontier providers. Use its own desktop/workbench UI or bring its capabilities into Claude Code, Cursor, Codex, OpenClaw, and other compatible tools through the CLI and MCP. Local-only work can run offline once its models and dependencies are installed; frontier calls and network integrations still require connectivity and may send their selected context to the configured provider.

The primary domain is **agentnekko.com**; **nekkoagent.com** and every earlier domain (kotrain.com, kotrain.app, nekkos.app, nekkos.dev) permanently redirect to it with paths and query strings preserved. The repository is **nekko-labs/agent-nekko**, the npm package and CLI command are **agent-nekko**, the bundle id is **dev.nekkolabs.agentnekko**, and installers are named **AgentNekko-…**.

Compatibility is a requirement of the rename, not a phase of it. The `kotrain` and `nekkos` commands remain as aliases; `KOTRAIN_*`/`NEKKOS_*`/`OPENPAW_*` environment variables are still read behind `NEKKO_*`; an existing `~/.kotrain` data dir keeps being used; the desktop app adopts its earlier-brand profile on first run; `kotrain://` and `nekkos://` deep links still resolve; and install targets and spec methodology ids saved under an older name are folded onto the current one. Release assets and updater feeds published under an older name are immutable and stay where they are.

The personality is a capable, approachable agent nearby, with a restrained secret-agent influence rather than spy parody. Clear task status, quiet confidence, and generous whitespace take precedence over mission jargon, decorative surveillance metaphors, or a heavy space theme.

Quality bar: on par with Zed / Cursor / Warp / OpenClaw, generous whitespace, minimal chrome, dark/light themes, fast.

The persona/mascot is **Nekko** (formerly Aphelion), a 2D hand-drawn outline cat with a subtle secret-agent look: slim sunglasses, a discreet earpiece and short coiled wire, and a folded collar with a small tie. The reflective helmet treatment is gone. Her full body is a slender stick-cat silhouette with long line-art limbs and a narrow torso, not the older rounded astronaut/loaf body. At rest she leans one shoulder against a short local representation of the app edge, ankles crossed with one paw relaxed, like an agent waiting for the next assignment. The edge is part of the drawing only; the full rail divider remains hidden while collapsed. Sunglasses lift above closed eyes while sleeping or stretching so expressions remain readable. The miniature working icon simplifies the same head details for small sizes, and the portrait includes the collar without clipping. Website hero and social artwork reuse the app's exact leaning pose. The website favicon and packaged desktop/PWA/installer icons use the exact miniature secret-agent head on the dark-green tile, replacing the old orbit mark.

The ink and paper follow each theme, with ginger ears/tail and ink-filled glasses/tie. The full mascot retains its frame-by-frame "line boil" wobble and the activity system shipped in PR #140 (T124). Every state uses the same slender proportions: leaning while idle, pushing away from the edge and spinning when the user returns, making a long limber stretch during active pauses, standing and bracing against the edge to inspect a bug while the model works, and slumping against the edge after sustained inactivity. Pose timing, reduced-motion handling, offscreen pause behavior, and right-facing placement remain unchanged.

## Why It Exists

People who want to run AI models locally are stuck choosing between two kinds of tool, each blind in its own way:

- **Local chat UIs (LM Studio, Ollama front-ends)** are *chat-only*, a great model runner with a chat box, but with no awareness of your files or projects. The model can talk about your work but can't actually do it.
- **Terminal CLIs (Claude Code, aider)** have agentic power but are *blind*, you can't see what changed without `git diff`, and editing means leaving the tool.

Agent Nekko exists to collapse that gap: easy local-model setup **and** a model that works inside your real codebases, with everything it does visible.

### Positioning (carry into website + README)

**AI help on your computer. For coding and everyday work.** Lead with what people can do: get help writing and coding, automate repetitive tasks, and choose AI running on their computer or an online service. Explain that a model is the AI they choose, and local AI runs on their own computer. Do not require readers to understand "frontier", "harness", "runtime", "CLI", or "MCP" before they understand the benefit. Technical setup details remain available farther down the page with short explanations.

The five main marketing headings are **Use AI on your computer or online**, **Choose the right AI for the job**, **Automate repetitive work**, **Manage your AI models in one place**, and **Control your computer by voice** (visibly Planned). Section titles describe concrete actions rather than agent/spy metaphors. Agent Nekko complements existing tools instead of requiring people to abandon their preferred interface; its differentiator remains combining available local compute with online models. Simplifying the language must preserve setup requirements, paid-provider costs, privacy boundaries, and the distinction between available and planned features.

### Messaging pillars

1. **Frontier and local, working together.** Use Agent Nekko as your primary harness/UI, or connect through its CLI and MCP from compatible tools such as Claude Code, Cursor, Codex, and OpenClaw. Bring your own frontier providers and local model servers.
2. **The right model for the task.** Help users select models for a prompt and delegate concrete work to local or cheaper models while reserving frontier capability for demanding planning. Local inference can avoid per-token API charges but still uses hardware, power, memory, and time. Explain routing decisions and never silently cross an offline boundary.
3. **Automation in one place.** Manage scheduled tasks, watchers, and workflows alongside interactive agent work. Reusable procedures support agent, skill, shell, and nested workflow steps with bounded retries and visible outcomes.
4. **Simpler model management.** Discover and connect local runtimes, manage supported model lifecycle actions from the same app, and mix managed and existing servers as support grows. Installing and supervising an inference runtime so a separate server app is unnecessary is a product goal, not a claim that an inference engine is already bundled.
5. **Control your PC offline, with safeguards.** Tell Nekko what you want by text or voice and let it perform supported local computer actions within permissions you choose. One-click guided setup selects a compatible local intent LLM, text-to-speech (TTS), optional speech-to-text (STT), and required runtimes based on the machine and each component's minimum requirements. The experience includes model/setup explanations, action previews, sensitive-action confirmations, and an immediate stop control. This is a major planned product capability, not available in the current release.

### Roadmap: beyond one machine

These are aspirations, not generally available capabilities or launch promises:

- **Team hardware and distributed work:** opt-in workers pool available machines for model inference, agent tasks, and workflows, with permissions, capacity reporting, isolation, cancellation, and clear ownership.
- **Local task runners:** expand today's local shell/agent workflow foundation into a practical alternative for jobs otherwise consuming hosted CI credits. GitHub Actions workflow compatibility and untrusted pull-request execution require their own design and security review; neither is implied by local shell steps.
- **Team workflows:** shared definitions, run coordination, access controls, and auditable outcomes across a team.
- **Optional cloud runners:** explore only if users want them. A paid service must remain optional and must not weaken the local-first experience.

Existing cloud prototypes and older branding elsewhere in this spec describe implementation history or parallel work, not a requirement to launch a hosted product before the local Agent Nekko experience.

## Who It's For

- **Developers who want to use local models for real work**: people running LM Studio / Ollama / vLLM who are tired of a chat box that can't touch their files, and want an agent that reads, edits, and runs in their codebases.
- **Claude Code / aider / terminal-CLI users** who want the same agentic power but with an IDE-like surface (file tree, diffs, inline edit, visible context).
- **Privacy-conscious / offline users** who want everything to stay on their machine, and, with Cloud, a zero-data-retention path that still keeps inference local.
- **People who want an approachable local PC assistant** without assembling an intent LLM, speech models, runtimes, and hardware settings themselves. Voice is optional; typed control and visible confirmations must remain first-class.
- **People who want to reach their home/office model from their phone** (the headline Cloud feature).

## User Journeys & Experiences

### Editions, same engine + UI, different runtime

Agent Nekko ships the **same engine + same React UI** in several runtimes; from the user's point of view it's the same product wherever it runs (only the host transport differs, see `TASKS.md` and [spec-web-and-hosted.md](spec-web-and-hosted.md)):

- **Desktop** (Electron), the primary experience, available today (installers on GitHub Releases).
- **Self-hosted web**: `npx agent-nekko` or `npm run web` starts a local server that serves the same UI in a browser; offline-first.
- **Docker**: `docker compose up`, workspaces as mounted volumes, local models reachable via `host.docker.internal`.
- **Agent Nekko Cloud** (paid), managed hosting with subscriptions, an always-available **Zero-Data-Retention** mode, cloud chat-history + file management, and **phone connectivity to your locally-running model** via a secure relay.

### Setting up a local model

A user opens the app and goes to **Models**. Auto-discovery probes common localhost ports (Ollama 11434, LM Studio 1234, vLLM 8000, plus `127.0.0.1` to catch IPv4-only servers). They add or confirm a server, test the connection (green Connected / Offline), and the model list populates. Cloud providers are added the same way, grouped into **Local** vs **Cloud** sections. Favorites pin to the top of the picker.

Each local server then renders as a **runtime card**: a power toggle that really starts and stops it, its address ready to copy or edit in place, and the models it currently holds with the real split between GPU and system memory. Picking a model opens a **fit drawer**, where one context slider drives a live memory projection: weights, KV cache, and runtime overhead stacked against what the machine actually has free, with a marker where that memory runs out. Dragging the slider past what the machine can hold turns the bar amber and then pushes it past the marker, so a user learns a 64k context will spill onto the CPU *before* waiting through the load rather than after. Underneath, one plain sentence says what will happen and why ("12 of 32 layers will run on the CPU, because the KV cache alone needs 14.2 GB"), and up to three one-click fixes offer a smaller context, a cheaper KV cache, fewer parallel slots, or a smaller build. Expert controls (parallelism, KV cache type, GPU offload share, TTL) sit behind an Advanced disclosure, and settings a server only reads at startup are shown as the exact environment line to set, marked restart-required, rather than as a control that would silently not apply.

### First-run setup (planned onboarding wizard)

The first launch opens a calm, full-screen setup wizard over the app; every step can be skipped (a per-step **Skip**, plus **Skip setup**), and it never auto-shows again once dismissed (Settings can replay it). Three skippable steps:

1. **Theme.** System-match, Light, Dark, and a set of elegant tech presets, each shown as a circle filled with a gradient of its palette so the choice is visual, not a word list. Clicking previews live.
2. **Providers.** Two groups: **online** (Claude and ChatGPT lead with one-click *subscription* sign-in so a Pro/Max or Plus/Pro plan works without metered API fees, API keys remain the secondary path, plus OpenRouter and a generic OpenAI-compatible endpoint) and **local** (auto-discovery surfaces running Ollama / LM Studio / vLLM servers for one-click add, and an **Agent Nekko** card offers the app's own managed local-model path).
3. **Integrations.** Two groups: **use Nekko inside other tools**, which installs the app as an MCP subagent into detected agent CLIs (Claude Code, Codex, Cursor) with one click, and **connect your apps** (GitHub, Linear, Slack, Discord, Jira, Teams, Gmail, Drive) so workflows and context can reach them.

### Signing in with a subscription (planned)

A user with a **Claude Pro/Max** or **ChatGPT Plus/Pro/Business** subscription clicks **Sign in with Claude** / **Sign in with ChatGPT** on the Models page (or in onboarding), approves in the browser tab that opens, and lands back on a connected provider marked **Subscription**, no API key, no per-token billing. The flow uses the same public OAuth sign-in the vendor's own CLI uses; the honest caveat shown next to the button is that the vendor's terms are written around their own apps, so the subscription path is offered as-is and the API-key path remains fully supported. Headless or remote setups get a paste-the-code fallback, and anyone already signed in to the Claude Code or Codex CLI can **import** that session in one click instead of repeating the browser flow. Sign out revokes the local token; a failed refresh prompts re-auth rather than silently falling back.

### One-click setup for safe offline PC control (planned)

**The experience:** a user who does not want to assemble an AI stack opens **Set up offline PC control**. Nekko inspects their machine, explains which models and runtimes fit, and shows the download size, disk/memory budget, supported actions, and permissions required. One **Set up** action then downloads or imports, verifies, installs, configures, and checks the complete local stack. Separate operating-system permission dialogs and license acceptance still require the user's approval; one click never means silently granting access or bypassing security controls.

The stack includes a local **intent LLM** that turns a request into a bounded, structured action plan, **TTS** for spoken responses, **STT** when voice input is enabled, and any supported runtime or computer-control adapter those components require. Text input and captions remain available; push-to-talk is the initial voice path rather than always-on listening. Audio and captured screen content are local and ephemeral by default. Local spoken intent is a request to evaluate, not permission to run arbitrary generated shell commands.

**Hardware-aware selection:** check OS/version, CPU architecture and supported instruction/backend features, total and available RAM, GPU/backend/driver compatibility, dedicated VRAM versus unified memory, and available installation disk space. Compare those facts with versioned, verified model/runtime requirements, supported languages, and required intent/STT/TTS capabilities. Fit the whole concurrently loaded stack, including runtime overhead, context/KV memory, and headroom for the user's normal applications. Do not double-count unified memory, assume separate GPUs form one pool, or equate a small download with a usable runtime footprint. Distinguish minimum compatibility from a recommendation expected to feel responsive. Validate with a short on-device warm-up and benchmark; present measured readiness rather than inventing performance claims.

If the recommended stack does not fit, offer a smaller supported model, reduced concurrency, or a tested CPU-only path with its trade-offs. If none meets the minimum requirements, say exactly what is missing and keep setup blocked. Unknown hardware support is **unverified**, not a pass. Never silently install an incompatible model or switch to a cloud provider. Users can review or override recommendations only within supported combinations and keep using an existing compatible runtime rather than being forced to replace it.

**Computer control:** supported local actions should include opening an approved application, switching to an approved window, adjusting a supported local setting, and entering text into a confirmed target. Scope access by app/window and action, prefer semantic/accessibility APIs over blind coordinates, and show the intended action before execution. Recheck the target immediately before acting and stop if focus, permissions, or observed state changed. Ambiguous voice recognition or low-confidence intent triggers clarification, not a guess. Treat text seen in applications, documents, and web pages as untrusted content, never as authorization to override the user's request.

**Safety contract:** a deterministic action broker validates the model's structured proposal against granted capabilities. No unrestricted shell or elevated permissions by default. Sending messages, purchases, destructive changes, credential/security changes, and other sensitive actions need explicit, action-specific confirmation; a model response or background audio cannot approve itself. Provide an always-visible stop button and keyboard shortcut, interruptible action boundaries, bounded execution, clear failure/partial-completion reporting, and a local activity log with sensitive content redacted. Undo is offered only for actions with a real, verified inverse; do not promise universal rollback. Revoking a permission stops related queued actions. These controls reduce risk but are not a guarantee that a model can never make a mistake.

**Offline means end to end:** initial provisioning needs internet access for approved downloads unless the user imports a verified offline bundle. Once ready, intent recognition, speech input, speech output, and supported PC actions run locally with no account, cloud fallback, remote telemetry, or network access required. Online actions are unavailable in this mode. Verify the experience with external network access blocked, not merely by pointing chat at localhost. A local server capable of proxying to the cloud is not automatically a verified offline runtime.

**Availability and boundaries:** current hardware telemetry, file/shell tools, model discovery, and guardrails are reusable foundations, not an implemented voice/desktop-control stack. The current chat **Offline** toggle disables all tools; this feature needs its own explicit local-only action policy and must not be implemented by weakening that existing toggle. Build a platform/action support matrix for macOS, Windows, and Linux and expose unsupported OS capabilities honestly. The **requirements evaluator now exists** (AN9b): `machineReadiness` probes the machine (OS/arch, provable CPU features, backends, per-device VRAM or unified memory, RAM, free disk) and evaluates it against a versioned, curated catalog of runtime/intent/STT/TTS components, returning `recommended`/`compatible`/`insufficient`/`unverified` per role with structured reasons and a combined concurrently-resident budget; an unprobed fact yields `unverified`, never a guess. Still to build: automatic provisioning (AN9c), the voice pipeline (AN9d), the permission-scoped control broker (AN9e), the setup/control UI that surfaces this report (AN9f), and end-to-end safety/offline verification.

### Delegating frontier planning to a local worker

The lead agent can delegate a scoped task through `spawn_agent` with optional `provider_id` and `model_id` targets. Leaving both out preserves the parent's model. Changing provider requires a known exact model ID; the host checks the configured, enabled target and its model list before creating the child. Unknown, unavailable, disabled, or known non-chat models produce an error, never a silent fallback to a different or paid model. The child appears in the existing nested session UI with its selected provider/model and inherits the parent's execution policy and disabled tools. Ask mode and the ask-everything sandbox require approval before starting a sub-agent or calling an MCP tool, so indirect execution cannot bypass that boundary.

This first implementation is **explicit cross-provider delegation**, not automatic price/capability/resource optimization. The lead receives enabled provider IDs and labels, not credentials, and must ask for a known model rather than invent an ID. An opt-in local-worker default and a routing-decision UI remain planned. Incognito delegation is blocked because child sessions are persisted; it must not quietly retain an incognito task.

The existing **Offline** chat mode is deliberately narrower than normal local-agent work: it disables tools and connectors. The host now also rejects cloud or non-loopback provider endpoints before making a request, prevents unoffered tool execution, skips connector fetching in offline context previews, and suppresses hidden post-turn spec refreshes. This is endpoint-policy enforcement, not an operating-system network sandbox; users still control whether their local inference server proxies requests elsewhere. Broader independent model actions, including explicit spec generation, need the same privacy audit before claiming application-wide network isolation.

### Working in a codebase

The user wires one or more **folders** into a chat (multi-root), choosing one primary folder and any number of supporting folders in the Context Inspector's Folders section. The workspace gets indexed (file tree + code outline + search), with index search and workspace memory spanning the selected folders while the agent's working directory remains the primary. They talk to the model in a unified **Chat** surface, messages render as speech bubbles, and reasoning appears above each answer as a collapsed summary such as "Thought for 3s" (expandable to inspect the reasoning). A multi-step turn's working steps (reasoning, tool calls, and inter-tool narration) fold into a single collapsible **activity group** ("Worked on 6 steps · read_file, grep") so a long run reads as one expandable line instead of a wall of "Used `<tool>`" rows; only the final answer stays a bubble. Risky commands trigger an approval prompt. Each user prompt reveals a subtle on-hover action row (its timestamp, Copy, Edit & resend, and **Reset here**, which rewinds the chat to that message and re-runs it), replacing the old single Regenerate button. If a local model returns an empty response mid-loop, the reply retries once with a nudge and, failing that, surfaces a clear marker instead of stalling silently. If a model instead **degenerates into repeating itself**, the reply is cut off the moment the output collapses into a cycle, keeping everything it wrote before the loop and saying plainly what happened and what usually helps, rather than streaming the same sentence for minutes. A live subtext under the conversation tracks the in-flight reply (elapsed, tokens/sec, tokens generated) and keeps a last-reply summary when idle. **Tokens/sec is decode throughput**, output tokens over the time the model actually spent generating them, summed across the reply's steps: it deliberately excludes prompt processing, tool runs, and approval waits, so it matches the figure the local runtime reports rather than being dragged down by however long the turn happened to take (Ollama's own `eval_duration` is used where it's offered; other providers are timed from first token to the usage report). Single-digit rates keep a decimal, since 8.6 and 9.4 tok/s are different answers to "is this model fast enough". The UI says **reply** for a chat exchange and **iteration** for one cycle of a long-running run; "turn" is gone from the surface. Markdown renders on both sides of the conversation, so a dashed list typed into the composer comes back as real bullets rather than raw dashes. The composer accepts pasted images and has a **+** menu for a photo, file, or folder; attachments sit in a thumbnail strip inside the composer card, and right-clicking any chat image offers Copy or Save. Images are sent to vision-capable models as multimodal messages, with larger previews and a full-size lightbox on click. Invoking a `/skill` adds a compact usage chip while keeping the user's own input separate; the full skill instructions still go to the model. Above the composer, a two-row instrument strip separates **how this agent runs** (mode, tools, and the Offline / Incognito privacy switches on the right) from **which brain it uses** (model, thinking, effort, plus Automate), and the context readout counts the draft as you type it, in the strip and in the Context Inspector alike. Per-chat control modes (Ask / Guardrails / YOLO, plus Offline and Incognito) govern how much it confirms.

### Editing, reviewing & previewing, without leaving the app

Files open as panes right in the workbench: a dedicated **Files** side-pane lists every workspace root and can dock left or right (left by default), collapse, and resize; its tree opens files as tabs alongside chats and terminals. Markdown is rendered or code opens in a mono editor, with an integrated browser pane for the live preview beside the code. When the agent edits files, a **Changes** panel shows a line diff and the user keeps or reverts at line/file/all granularity. Reviewing AI-made changes, browsing a preview, and writing better prompts (via the always-on prompt analyzer) all happen in one calm window. *(Planned next:)* the user drops a **+ comment** on a line and either queues it for the next prompt or runs it immediately, turning in-place review notes into agent work.

### Designing: draw it or describe it (Design tab)

The **Design** tab is where designs get made, a Claude Design-style surface with two ways in, both ending as a working prototype:

1. **Draw it.** A pen-and-touch-first sketch canvas (built to be used from an iPad or iPhone via the web edition: pointer events, Apple Pencil friendly, palm-safe `touch-action`). The user sketches boxes, arrows, and labels, adds an optional note ("mobile app, dark theme"), and hits **Generate prototype**: a vision model turns the sketch into a polished, self-contained HTML code prototype.
2. **Describe it.** Write a prompt ("a landing page for a sushi delivery startup") and watch a design pop up. Starter idea chips help the first prompt along.

Either way the concept lands on the board as a card and is **mirrored into the workspace as a real HTML file** (`nekko-designs/`, or an existing earlier-brand folder), so the user, or any agent, keeps iterating on it as code. Selecting a concept opens a side sheet with a **Refine** box ("make the hero darker", "add a pricing section") that regenerates the design in place, follow-up by follow-up: the user stays the designer, the model just drafts fast.

The board still holds **live snapshots** of the app's real pages. The user pins **notes** on a page or leaves a **comment** that they Add-to-prompt or Run-now. As the agent reworks the UI, the snapshots refresh live and an "updating" badge marks the page being changed; clicking it jumps to the agent doing the work. The board makes "what does my app look like, and what should change" a visual, direct-manipulation surface.

### Seeing exactly what the model gets (Context Inspector)

A toggleable right-side panel makes context legible. **Sources** lists the folders wired in, attached files, the chat's `SPEC.md` (with Build-from-chat / Live controls), and **Guidelines**: detected guideline files (AGENTS.md/CLAUDE.md) plus memory entries, each with its own enable/disable control. Guidelines sits above the Spec panel, while **Breakdown** is a live view of exactly what's entering the prompt on the next reply (files, guidelines, memory snippets, connector data, index snippets), each item toggleable/pinnable with token counts, plus a context-window headroom bar.

### Living spec from a conversation

Any chat can synthesize a `SPEC.md` in its workspace from the conversation (using the session's own provider/model, one-shot). With **Live** on, the spec is rebuilt after every turn so it tracks design changes and new features as the conversation evolves.

### Training a model while you watch (Training tab)

The user opens **Training**, says what the model is for ("classify support tickets by urgency"), points at a dataset (Hugging Face, Kaggle, a local path, or a URL) and optionally a base model, and hits Start. That's the whole simple path; an **Expert levers** panel exposes the full configuration (framework, epochs, batch size, learning rate, metric + direction, experiment/time budgets, free-form constraints) for people who want control. A **data-scientist agent** then does the real work in a dedicated chat session, and the dashboard shows its progression live: stat tiles (best score, experiments, success rate, emergent niches, self-repairs, runtime), a **current champion** card, and the **idea maze**, a growing tree of every idea the agent tried, color-coded (tried / got better / best so far / running) with the path to the leader highlighted. The user can **guide the agent mid-run**: hints, new training approaches, or corrections fold into its next turn. Starting a run drops the user straight onto its live dashboard, where a "now" strip spells out what's happening (from "starting up…" through the currently-running experiment), and an **Artifacts card** makes the output concrete: it lists exactly what the run built (the trained model plus each harness file), where each lives, and how to use it, with one-click open in the OS file manager. The distinctive twist: a run can also produce the **harness for the model's use case**, an agent file (AGENTS.md), a skill, and/or a spec, so the output isn't just weights, it's a ready-to-use capability.

### Automating repeatable work (Workflows tab)

Some work isn't a conversation, it's a **procedure that should run the same way every time**, often without anyone watching. The **Workflows** tab is that surface, modelled on GitHub Actions but with the steps a coding agent actually needs: a step is an **agent prompt**, an installed **skill**, another **workflow**, or a **shell command**.

The part that makes it more than a script runner is that steps are **routed rather than merely sequenced**. Every step declares where the run goes when it succeeds and when it fails, and a route can point **back at an earlier step**, so the natural shape of real work is expressible: build, then verify, and when verify finds problems, go back to build and try again. Loops are bounded (a step can be re-entered a fixed number of times) so a workflow that never converges still stops and says so, rather than running forever. Steps also carry **retries**, a **timeout**, and a **continue-on-error** flag. Agent steps report their own outcome with a PASS/FAIL token, which is what lets an agent step be routed the way a shell step's exit code is; a run's agent steps all share one chat session, so a verify step sees what the build step actually did.

A workflow starts from whatever fires it: **by hand**, on a **schedule** (a cron expression or a plain interval), from the **CLI** (`agent-nekko workflow run <name>`, or `trigger <command>` to fire everything listening for it), from **Slack** (a channel, optionally filtered to messages containing a word), or from a **git provider event**, a pull request opened, updated, closed, merged, commented on or reviewed, a push, a tag, an issue, filtered by repo and branch. Provider events are **normalized across GitHub, GitLab, Bitbucket and other**, so a workflow reacts to "a PR opened" without caring whose vocabulary it was. One workflow can carry several triggers.

The tab is built for an install that accumulates **hundreds** of these. A left rail filters by search (which reaches into step bodies, not just names), enabled state, trigger kind, and category, and the list groups either **by category** ("what do I have?") or **by event listener** ("what happens when a PR opens?"), with a workflow appearing under every event it listens for. A row shows its state, step count, triggers, and how the last run went; expanding it reveals the **step canvas**, a node graph in the same visual language as the Skills tab, where failure routes are drawn in the danger color and a loop back to an earlier step dips under the row, so a retry loop is something you see rather than something you read. The same canvas doubles as the live run view, each node wearing that run's outcome, beside the attempt-by-attempt run log (with a link into any step's transcript) and that workflow's run history. Workflows are created from **templates** (a build/verify loop, a PR reviewer, a nightly maintenance sweep, or empty), edited in a dialog whose canvas redraws as you type and which flags steps nothing routes to and validates a cron expression against its next fire, duplicated, enabled/disabled, and deleted.

### Handing the agent a long-running goal

The user gives the agent **something to get finished** ("ship the CSV import end to end: parser, validation, tests, docs"), optionally with context and constraints, and the agent works it **plan-first** in three phases: **Plan** (it studies the goal and the workspace, then writes an ordered execution plan of concrete, verifiable steps), **Execute** (it works the plan step by step, marking each step active and then done, with a one-line outcome note, only once verified), and **Iterate** (when reality disagrees, a step fails, new work surfaces, it revises the plan and keeps going until every step is done and the goal is verifiably met). This is deliberately **not a model-testing surface** (that's the Training tab); it's a "work until finished" surface for real work.

The dashboard reads as **mission control, not a chat**: a big **"working for"** clock, live status plus a **phase chip** (planning / executing / verifying / finished), and the **live plan checklist** front and center, each step with its status glyph, note, and a progress bar, alongside a current-step card, goal-shaped stat tiles (plan progress, iterations, attempts, runtime), a **Mission control** card that surfaces the budgets the loop enforces (iteration budget, time budget), and a prominent activity feed of plan milestones, failures, and self-repairs. Course-correcting is a full-width **"Steer the mission"** console (deliberately one nudge at a time, folded into the next iteration, not a back-and-forth chat); the underlying agent transcript is still reachable via a low-key **Transcript** link. Under the hood a goal is **not just one ever-growing chat**: each iteration runs on a **bounded context window** (the last few turns; the brief re-injects the plan every turn), and the loop is **guaranteed to terminate**, the host enforces a turn budget and any time budget, and **detects a stall** (no measurable plan/experiment progress plus a repeating answer) to pause the run and ask for a hint rather than looping for thousands of iterations. Runs survive restarts and resume automatically; resuming a budget-capped run grants a fresh leg.

### Driving your home model from your phone (remote control)

The user opens **Settings → Remote access**, hits Enable (the managed relay is prefilled; a self-hosted relay URL works the same), and taps **Pair a device**: a QR appears carrying a **single-use pairing code that expires in 10 minutes**. They scan it from the phone (Agent Nekko app or any browser) and the phone shows up under **Paired devices** with a live connection dot. From anywhere, the phone now runs the full app against the home machine: start and manage chats, watch and steer training runs and goals, approve risky commands, browse the Command Center, with a **bottom tab bar** making the key surfaces thumb-reachable. Inference and tool calls execute locally under the machine's guardrails/sandbox.

Security is layered: the local agent dials out to the relay (no inbound ports), every payload is end-to-end encrypted (the relay routes only ciphertext, so relayed local-model use is inherently zero-data-retention), and on top of the transport every device must pass a handshake against the machine's **device registry**: unknown devices are denied unless they present a live pairing code, each device can be **renamed or revoked** (revocation kicks it mid-connection), and **Rotate secret** is the cryptographic kill switch that unpairs everything. Remote access survives restarts; the agent reconnects on boot. Full guide: [docs/REMOTE.md](docs/REMOTE.md).

- **Runtime control plane** `[shipped 2026-09-09]`, local model servers are started, stopped, and driven from their card rather than merely observed. Ollama is supervised as a child process we own (so it stops with its own handle and never outlives the app); LM Studio uses its real `lms server start|stop` lifecycle; **vLLM is connect-existing only** and says so, because it serves one model per process configured entirely at launch and no machine here can verify a spawn path. What each runtime offers is declared as **capabilities** rather than inferred from its name, so the UI never presents a control a server cannot honour, and a future bundled engine slots in without UI changes. Stopping a process **Agent Nekko did not start** asks for confirmation first and names what it would kill, replacing the previous silent kill-whatever-holds-the-port behaviour; a process we started stops without ceremony. A failed start surfaces the server's own captured output ("address already in use" and "command not found" are different problems), and a runtime that is not installed says so instead of offering a Start button that cannot work.
- **VRAM fit planner** `[shipped 2026-09-09]`, the answer to "will this model fit, where will it run, and why", *before* the load. Weights plus KV cache (`2 x layers x kvHeads x headDim x context x bytesPerElement x parallelSlots`) plus runtime overhead, measured against one memory pool, producing a verdict (fits / tight / spills / will-not-load / **unknown**), the estimated layers that land on the CPU, structured reasons carrying the numbers that drove them, and re-planned one-click fixes. Three honesty rules are load-bearing. **`unknown` is a first-class verdict**: capacity is never inferred from a model's name, so a missing layer count says so rather than producing a confident wrong number. **Unified memory is never double-counted**: on Apple Silicon the budget is system memory, not a card's VRAM plus RAM. And **multiple discrete GPUs are not pooled**, since without tensor parallelism a model must fit on one of them. Where a server reports less than the planner needs (LM Studio publishes no layer geometry), the projection is **partial rather than absent**: the real weights figure is still shown, a will-not-load verdict is still certain when the weights alone overflow the machine, and the missing terms are named. After a load the measured residency is reconciled against the projection and the residual feeds a per-runtime calibration record, so the overhead constant improves with use instead of staying a guess nobody can check.
- **Resource monitors** `[shipped]`, four live monitors, **CPU** load, **memory** use, **GPU** utilization, and **VRAM**, surfaced in two places that never fight for the same corner. A quiet always-on **monitor chip** sits bottom-right on **every tab** (one segment per enabled monitor, plus a VRAM micro-bar); hovering it opens the panel where each monitor is switched on or off and a per-GPU breakdown is shown. The chat's context panel carries the **full monitoring section** at its foot (CPU with core count and processor name, memory used/total with %, GPU utilization, VRAM used/total with % and per-device used/free). While that section is on screen the chip **warps into it**, shrinking, blurring and fading along a path that ends on the section (which answers with a one-shot glow), and flies back out when the panel closes, so the same numbers are never stacked on top of each other. **Switching a monitor off stops the work behind it**: the renderer polls only the probes the enabled monitors need, so turning GPU/VRAM off spawns no GPU probe and turning CPU/memory off samples no CPU times; with all four off the chip reads "Monitors off" and nothing is polled at all. CPU/memory come from `os` (portable, no native module, load measured as a delta between samples like a task manager). The GPU probe is **per platform**: `nvidia-smi` on Windows and Linux, and on **macOS** the accelerator driver's own counters read out of the IO registry (`ioreg -c IOAccelerator`), which needs no admin rights, unlike `powermetrics`. A Mac therefore reports its real GPU ("Apple M1 Max (32-core GPU)", live utilization) instead of the old "No NVIDIA GPU detected". Because Apple Silicon has **no dedicated VRAM**, the memory meter there renames itself **GPU memory**, measures the driver's current allocation against the unified pool, and says "unified with system RAM" so nobody reads it as a discrete card's VRAM; the dock names the probes it used (`os + ioreg`, `os + nvidia-smi`). A machine whose GPU can't be read says so plainly rather than naming a vendor it never checked for. Preferences persist in settings (`AppSettings.monitors`); one shared sampler feeds both surfaces so nothing is probed twice per tick.
- **Reasoning-model streaming** `[shipped]`, `reasoning_content` deltas (OpenAI-compatible) and `message.thinking` (Ollama) render into a collapsed, persisted "Thought for Ns" summary above each assistant answer; the full reasoning remains expandable.
- **Thinking toggle** `[shipped]`, for reasoning-capable models the metrics bar's "thinking" indicator becomes a per-chat **on/off toggle** (`session.thinking`) that turns reasoning on or off for that chat. Non-reasoning models keep the passive "streamed reasoning this turn" indicator.

- **Runaway-output backstops** `[shipped 2026-08-13]`, three things now bound a single response, because a local model that degenerates had nothing stopping it (one observed reply streamed 108,790 characters of reasoning, the same sentence 2,534 times, over nine minutes, and locked the window up). An **output cap** is sent to every provider as its native limit (`max_tokens` / `num_predict`; default 8,192, 256–200,000 in Settings → Agent loop), where openai-compat and Ollama requests previously carried none at all and ran until they filled their own context window. A **repetition guard** watches each stream and cuts it off the moment the output collapses into a cycle, cancelling the request, keeping the useful head of the reply, and ending the turn instead of spending the rest of the step budget on the same loop. And streamed deltas are **batched into frames** rather than committing React state per token, with the live buffers capped, so a fast or runaway reply can't freeze the transcript.
- **Runs survive being cut off** `[shipped]`, a long agent run is checkpointed as it goes, so an interruption costs you the last step rather than all of them. Every completed step (the assistant message and each tool result) is **written to disk the moment it lands**, before the event even reaches the UI, so a run killed mid-flight by a timeout, a dropped connection, a crash, or a quit leaves its finished work on disk instead of only in memory. A reply whose stream breaks **keeps what the model had already written**, marked as cut off, rather than vanishing behind an error (a tool call it was still emitting is dropped: it never ran and its arguments may be truncated). Pressing **Stop** goes through the same path, so a stopped reply keeps its partial answer and reads as "Reply stopped", not as a failure. The failure notice then offers **Resume** as the primary action: the transcript is left exactly as it is, any tool call that never got to run is answered with a stand-in saying so (which is what makes an interrupted transcript valid to send again), and the model is told to continue from where it stopped and not repeat the work above. **Start over** remains beside it as the honest name for the destructive option, which re-answers the prompt from scratch and discards the run. (Before, a timeout on a long chat reported only "Reply failed", and the single **Retry** button truncated the chat back to the last user message, throwing away every step it had completed.)
- **Tool-step budget (no more lost replies)** `[shipped]`, the agent loop is bounded by a **step budget** (default 80 tool round trips per reply, 5–400, set in Settings → Agent loop) that exists to catch a loop going nowhere. Reaching it no longer discards the work: the loop takes one final pass with the tools **withheld**, so the model answers with what it found and the next steps it would take, and the reply lands with an honest note naming the limit and how to continue. (Before, a long exploration hit a hard 12-step cap and the whole reply failed with "Reached max tool iterations".) The agent's operating principles also make it **diagnose blocked operations instead of retrying blindly**: an empty/unauthorized/not-found result (an empty `gh`/API response, a 401/403/404, "permission denied", an auth prompt) makes it stop and name the likely cause, a private or inaccessible repository, missing/expired credentials or `gh` auth, a wrong remote, or a rate limit, and say how to fix it, and it **ends every turn with an honest wrap-up** (what it did, what actually happened including anything blocked or unverified, and the concrete next step) rather than claiming a task is done when it isn't.

### Workflows (procedural automation)
- **Workflows tab** `[shipped 2026-08-13, replaced the Goals tab]`, GitHub-Actions-style automation where a step is an **agent prompt**, an installed **skill**, another **workflow**, or a **shell command**. Steps are **routed, not just sequenced**: each declares where the run goes on success and on failure, and a route may point back at an earlier step, so build → verify → back to build is a first-class shape (bounded by a per-step re-entry cap so a non-converging workflow still terminates and says why). Steps carry retries, a timeout, and continue-on-error. Agent steps end with a **PASS/FAIL token** so they can be routed like a shell exit code, and every agent step in a run shares one chat session so later steps see earlier work. Each run records every attempt (step, attempt number, outcome, output/error, and a link to the step's transcript); history is capped per workflow, and a run interrupted by a quit or crash is written off as interrupted on the next boot rather than looking stuck.
- **Triggers** `[shipped]`, per workflow, any number of: **manual**, **schedule** (a 5-field cron expression, parsed in shared so the editor validates it and previews its next fire, or a plain every-N-minutes interval), **CLI** (`agent-nekko workflow run <name>`; `agent-nekko workflow trigger <command>` fires everything listening for that command), **Slack** (channel + optional keyword), and **git provider** events (PR opened / updated / closed / merged / commented / reviewed, push, tag, issue opened / commented) filtered by repo and branch globs. Provider events are **normalized across GitHub, GitLab, Bitbucket and other**, so a workflow reacts to "a PR opened" regardless of whose vocabulary the webhook used. Every transport enters through one host door (`workflow:event`), which in the web edition is reachable as an HTTP endpoint for a Slack app or a webhook, so all of them match by the same rules.
- **Built for hundreds** `[shipped]`, the list filters by search (reaching into step bodies, not just names), enabled state, trigger kind, and category, and groups either **by category** or **by event listener**, a workflow appearing under every event it listens for. Groups collapse and cap their rows with a "show more", so a few hundred workflows stay navigable.
- **Step canvas** `[shipped]`, expanding a row (or opening the editor) draws the step graph as a node canvas in the same layered-node visual language as the Skills tab (the layout code is now shared by both). Failure routes are drawn in the danger color, loop-backs dip under the row as dashed edges, and terminal Done / Failed nodes close the graph. With a run selected the same canvas shows that run's per-step outcome and attempt count, so the shape of a workflow and how it last behaved are one picture.
- **Editing** `[shipped]`, create from a **template** (build/verify loop, PR reviewer, nightly maintenance sweep, or empty) or from scratch; the editor redraws the canvas as you type, warns about steps nothing routes to, and re-points any route left dangling by a deleted step. Workflows can be duplicated (arriving disabled, so two don't answer the same trigger by accident), enabled/disabled, and deleted (which takes the run history with it).
- **Integration triggers** `[shipped 2026-09-08]`, beyond manual/schedule/CLI, a workflow can fire from the user's connected apps: **connector triggers** poll the configured Linear, Jira, Slack, Discord, or Teams account on an interval for new matching events (polling is the default because a desktop app behind NAT can't receive inbound hooks), and a **webhook trigger** gives each workflow its own secreted URL (`POST /api/hooks/<slug>`) on the server/Docker editions, with an opt-in loopback listener on desktop. Every external event still enters through the single `workflow:event` door, so matching rules stay identical however the event arrived.
- **Action steps** `[shipped 2026-09-08]`, a fifth step kind that pushes results back out through the integrations: post a Slack or Teams message, comment on or create Linear/Jira issues, comment on a PR, set a commit status. Fields interpolate run context (`{{trigger.*}}`, `{{steps.x.output}}`, `{{run.status}}`), and the editor offers real pickers (channel, issue, repo) instead of raw payloads.
- **Local CI runner** `[shipped 2026-09-08]`, a workflow template that turns a machine into a private runner for git-host events: on `push`/`pr_opened` it checks out the ref, runs the repo's build/test steps locally, then reports the outcome back as a **commit status** (`agent-nekko/<workflow>`) and, on failure, a PR comment with the output tail. This is how a team spends their own hardware instead of hosted-runner minutes; it deliberately is *not* an implementation of the GitHub Actions runner protocol, and untrusted-PR execution needs its own review before enablement (see Scope Boundaries).

- **Hypergate integration** `[shipped]`, Agent Nekko pairs with [Hypergate](https://hypergate.app), the Nekko Labs MCP server runtime and manager, in one click from either side, and then runs it as a tab in this window.
  - **Detect.** Agent Nekko probes the local `hypergated` daemon at startup (host-side, so it works in every edition) and shows a card in Settings → MCP servers naming its version, its managed-server count, and its port. ## Scope Boundaries

- **No native node modules**: keeps Electron rebuild pain away; ripgrep/git are spawned via child_process with JS fallbacks. (Technical constraint; see `TASKS.md`.)
- **Not a full IDE**: the file editor is a lightweight mono textarea (+ rendered markdown), not Monaco/CodeMirror; no language servers, debugger, multi-cursor, or refactoring tooling. The browser pane is a preview/utility surface, not a hardened general web browser. The Design board (planned) shows snapshots, not an editable vector canvas.
- **Cloud never runs your shell/filesystem tools on our servers**: inference and tool calls always execute on *your* paired machine. The cloud is a sync + relay + billing layer, not a remote executor.
- **The OSS app never checks a license**: paid features are gated server-side in Cloud only; the open-source editions are fully functional and free.
- **The relay is a dumb pipe**: it authenticates/routes and forwards ciphertext; it does not inspect or store message bodies.
- Pricing tiers (Free OSS / Pro / Team) are drafts pending cost modeling, see [spec-web-and-hosted.md](spec-web-and-hosted.md) §6.
- **Workflows don't execute untrusted code from strangers**: a git-triggered workflow that checks out a pull request runs that contributor's code with this machine's tool access. Local CI runner templates must only auto-fire on trusted refs (own branches, collaborators' PRs); running arbitrary fork PRs is an explicit opt-in with sandboxed (yolo-off, approval-gated) tool policy, not a default.
- **Subscription sign-in rides first-party OAuth clients**: the Claude and ChatGPT subscription flows use the public OAuth client of the vendor's own CLI. Vendor terms are written around their own apps, so the feature is offered as-is, clearly labelled, with the API-key path unaffected. If a vendor cuts it off, the app degrades to API keys, not a broken product.

Relay scaling beyond one machine needs sticky routing (fly-replay by room) when it matters.
- E2E key-management UX (recovery vs zero-knowledge trade-offs).
- Mobile: PWA first, or native shells later? (Native Capacitor shells now exist; PWA also works.)
- Exact ZDR boundary for cloud-configured (non-local) providers without ZDR tiers, likely "not allowed in ZDR workspaces."
- Do desktop + local web share one data dir by default, or separate? (Lean: share, so the web UI sees your desktop sessions.)
- "Agent Nekko" as a local provider in onboarding presumes managed in-app inference (the AN9 track). Until that lands, the onboarding card deep-links to the Models page's local setup; it should become a real one-click managed-model install when AN9 exists.
- Microsoft Teams reads need Microsoft Graph OAuth, which requires an app registration; v1 supports posting via incoming webhook and reads via a pasted token. Whether to register a first-party Nekko Graph app is open.
- Full Gmail/Drive OAuth flow (needs Google client creds); macOS signing + notarization is **done**: the `nekko-labs` org secrets are in place and releases from v0.6.0 on are Developer ID signed and notarized (see [docs/signing.md](docs/signing.md)). Windows Authenticode is pending SignPath Foundation. The npm publish of `agent-nekko` needs an npm credential that may publish it: the v0.6.1 run failed with a 403 on `kotrain`, so either `NPM_TOKEN` must be able to publish the new name or the first publish is done by hand, after which a Trusted Publisher can be bound to `nekko-labs/agent-nekko`.
